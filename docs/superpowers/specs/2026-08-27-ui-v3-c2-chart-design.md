## 2. 结构裁定：紫微棋盘与保留三块放哪

两份稿都没说死紫微棋盘的归属：移动版 `5b` 只给了一条入口条「紫微十二宫 · 三段式解读 →」，桌面 `8b` 的右列写明是解读、通篇没提紫微。**owner 2026-08-26 裁定：紫微留在 `/chart` 页内，入口条改锚点**；保留的三块（西方盘 / 自我画像 / 当下时序）**全部保留、按新设计语言重排**。

### 2.1 左右分列规则

`06-desktop` §3 的原则是「**左列是不动的事实，右列是可滚的解读**」。按此分列，但**紫微棋盘与西方盘归右列，不归左列**——理由是宽度，不是语义：

| 位置 | 内容宽度 | 4×4 棋盘每格宽（3 道 6px 间隙） |
|---|---|---|
| 左列 | 1120 − 56×2 = 1008 → 440 − `padding-right 32` = **408px** | (408−18)/4 ≈ **97px** |
| 右列 | 1008 − 440 = 568 − `padding-left 40` = **528px** | (528−18)/4 ≈ **127px** |
| 移动端 390 视口 | 390 − `px-5`×2 = **350px** | (350−18)/4 ≈ **83px** |

每格要放宫名 + 四化标签 + 主星（含亮度，形如 `紫微(庙)`）+ 辅星 + 杂曜。**97px 比移动端的 83px 只宽 14px，星名会大面积折行**；127px 才明显好于移动端。故：

- **左列**（严格按 `8b` 稿）：日主行 + 三 chip + 五行盘 + 八字四柱 + 大运三格 + 流年 chip 行
- **右列**：三段式解读 → 紫微棋盘 → 西方星盘 → 自我画像 → 当下时序

这样左列保持短，「不动的事实」这个体验才真的成立——若把棋盘和西方盘都塞进左列，左列会高出右列一大截，两列独立滚动的意义反而被稀释。

⚠️ **这是本波唯一一处偏离「左=盘 / 右=文」字面语义的决定**，理由是可测量的宽度约束（上表）。实施时若发现 127px 仍不够（例如某宫主星 3 颗以上带亮度），**不要偷偷缩字号**，按 §9 的处置报上来。

### 2.2 DOM 顺序：桌面与移动共用一份

**两个断点用同一份 DOM 顺序**，只由 `TwoColumn` 决定落在哪一列——不写两套顺序。移动端把左栈、右栈依次纵向铺开：

```
日主行 → 三 chip → 五行盘 → 八字四柱 → 大运三格 + 流年 chip
  → 目录两行（紫微十二宫 ↓ / 三段式解读 ↓）      ← 5b 的入口条改锚点
  → 三段式解读 → 紫微棋盘 → 西方星盘 → 自我画像 → 当下时序
  → 免责一句
```

⚠️ **右栈内「解读」排在「紫微」之前，与 `5b` 入口条的字面顺序（紫微在前）相反**，这是刻意的：桌面 `8b` 右列稿子本身就是「进度条 + tab 打头」，而解读是本页主载荷；移动端由目录两行提供锚点跳转，顺序不影响可达性。**若 owner 更看重与入口条字面一致，这条可以翻转，翻转成本很低（调换两个区块）。**

## 3. 断点与版式

沿用 C1 已建的三档（`06-desktop` §2），**不新增断点**：

| 断点 | 布局 |
|---|---|
| < 768px | 单列，`px-5` |
| 768–1199px | 单列居中 `min(100% - 96px, 720px)` |
| ≥ 1200px | `TwoColumn` 两栏，左列 **440px** |
| ≥ 1600px | 内容列上限 1120px，**不拉第三栏** |

⚠️ **断点单位陷阱（CLAUDE.md 已记，C1 踩过）**：自定义断点一律 rem。`--breakpoint-xl` 现为 `75rem`，**不要改回 px**——Tailwind 4 无法跨单位排序 media 块，混单位会让低断点反压高断点，且 class-name 断言抓不到。
⚠️ **桌面专有样式必须断点门控**，且凡 `xl:` 与更低断点在同一属性上语义互斥处用 `max-xl:`，不要裸 `md:`/`lg:`。

## 7. 大运三格：数据风险与空态

`03-screens` `5b` 要求「大运列表：三行（前一运 / 现行 / 下一运），现行走强调手法；下接流年 chip 行，当前流年朱砂描边」。

数据已在冻结命盘里：`packages/core/src/types/chart.ts` 的 `BaziChartSchema.luckPillars`，形如 `{ startAge, startYear, pillar }[]`，另有 `currentLuckPillar?: string`。

⚠️ **但 `luckPillars` 的 zod 定义是 `.default([])`**——**早期冻结的命盘可能压根没有这个字段，解析后是空数组**，三格会渲染成空白。这正是 CLAUDE.md 记的那类「新旧冻结命盘通吃」问题。

**要求：**
1. 实施时**先去生产库抽查存量冻结命盘到底有没有 `luckPillars`**（`profiles` 表里的冻结 chart JSON），把实际比例写进报告。**不要靠推断。**
2. 无论抽查结果如何，**必须实现空态兜底**：`luckPillars` 为空或找不到现行运时，整个大运三格区块**不渲染**（而不是渲染三个空格），流年 chip 行同理。
3. 「现行运」的判定优先用 `currentLuckPillar`；它缺失时按 `startYear` 与当前年比对推出。**两条路径都要有测试。**
4. **流年 chip 的年份序列是展示层算术**（现行运的 10 年跨度），不是命理推算，可以在展示层算；但**四化不许在展示层算**——那是 `computeZiweiHoroscope` 的活，本波不碰。

## 9. 测试策略

沿用 A/B/C1 口径，并针对 C1 暴露的**六类同型缺陷**逐条设防。写每一条断言前必须回答：**「如果这条实现被回退，它会不会变红？」答不上来就别写。**

C1 实际踩过的六类，本波逐条防：

| # | 缺陷类型 | 本波怎么防 |
|---|---|---|
| 1 | 断言被同用例其他断言完全覆盖（零独立区分力） | 每条断言单独 mutation 复验，不是整个用例 |
| 2 | matcher 字符串与实际文本**不可能**匹配（U+3000 全角空格） | 断言前先打印实际 `textContent` 核对 |
| 3 | 用例名与用例体名实不符 | 改实现时同步改用例名 |
| 4 | 断言过浅（只查存在，不查行为） | 查行为，不查存在 |
| 5 | 断言的**判断条件恒假**（`typeof a === "string"` 对 Error 对象） | 断言里若有类型判断，先验证实际类型 |
| 6 | 断言的**维度覆盖不到失败模式**（class-name 断言抓不到 CSS 级联顺序） | 凡涉及层叠/顺序/单位的，断言打在**构建产物**或改用结构性互斥（`max-xl:`） |

本波特有风险点：

- **大运空态**：两条路径（`currentLuckPillar` 有 / 无）+ `luckPillars` 为空 三种情况都要有用例。
- **`ZiweiBoard` 落位**：断言宫位按 `branch` 落位，**不是数组顺序**——用一个 branch 顺序与数组顺序不同的 fixture，否则断言零区分力。
- **`ReadingTabs` tab 切换**：断言切换后**结论大字与正文都变了**，不只是 tab 高亮变了。
- **两栏落位**：断言左栈/右栈各自的内容归属，且 DOM 顺序只有一份。
- **保留三块未被删**：三条存在性断言（这是防「静默失踪」的回归网）。
- **i18n**：补一条 `locale="en"` 渲染断言；命理术语（`SIGN_CN`/`STRENGTH_CN`/`ELEMENT_LABEL`）**保持中文**也要有断言守住，防止后人「顺手翻译」。
- ⚠️ 本波若动 `packages/core` 要跑三个包。`packages/core/tsconfig.json` 的 `include` 只有 `["src"]`，写在 `core/test/` 的类型断言是**惰性的**。
