# EP-jiao — 掷筊问事（「灵」收缩为占卜问事）

> 状态：设计定稿，待写实施计划 · 作者：claude · 日期：2026-08-25 · 关联：`.agent/BACKLOG.md`、`docs/superpowers/specs/2026-08-19-dream-interpretation-design.md`（记录机制与红线的同款先例）、`.agent/CURRENT.md` EP-spirit 三期交付记录

## 0. 背景与决策

owner 提出：为占卜今日运势加入「掷筊杯」形式（含动画）。澄清过程中范围发生了两次实质变化，最终定为：

1. **不是今日运势的入口**，而是**问具体事情**的独立形态——掷筊在传统语境里是对一件具体的事问神明，用在「今日运势」上语义不合（运势是算出来的，不是问出来的）。
2. **并入「灵」的入口，并把「灵」的产品范围收缩为占卜问事**——`/spirit` 主界面不再是「随便聊」，而是「先对一件具体的事掷一卦」。

**「收缩」收的是起手姿势，不是对话本身**（owner 明确）：掷完筊、灵解读之后，用户可以自由追问，对话体验与现状无异。因此 `SpiritPanel` 的流式/历史/Paywall 骨架整个复用，改的只是「进门要先掷筊」这一层。

### 0.1 为什么真随机在这里是成立的（与「全仓零随机」原则的关系）

调研确认：`packages/core/src`、`packages/llm/src`、`apps/web/{app,lib,components}` 中 **`Math.random` 出现次数为 0**。所有「看起来随机」的变化都是日期字符串的确定性哈希（配图轮选 `hashStr(dateStr) % list.length`、花窗形状 `shapeOf(seed)`）。

这条原则真正约束的是**排盘计算的完整性**——命盘不能在两次刷新之间变，配图做成哈希是为了「同一天看到的东西一致」。**掷筊不是计算，是仪式**：现实里没人指望两次掷出同样的结果，传统做法本身就允许连掷（笑筊的本义就是「问得不清楚，重问」）。若同一个问题永远得到同一个答案，那不是掷筊，是查表。

因此掷筊用真随机，不违背该原则——但**必须在代码里显式注释说明此处为何是例外**，否则未来任何 agent 看到都会当成违规想「修」掉。

### 0.2 与产品定位守护栏的关系

守护栏明文禁止神谕式断言（`FENGSHUI_GUARDRAILS`：「禁断祸福」，日历免责：「启发性参照，非吉凶预言」，`SYNTHESIS_GUARDRAILS`：「不做医疗/法律/财务/生死预测」）。对任意人生问题给是非答案，比每日运势场景**更**危险。

解法是把筊象定位成**心理投射媒介而非答案**——与 PRD 已写明的「命盘作为**心理投射界面**」同构，也落在 `FENGSHUI_GUARDRAILS` 已认可的「用**仪式感与掌控感**的框架呈现」这一表述内。荣格派用塔罗/易经即是此用法：价值不在结果说什么，而在你看到结果时的第一反应（掷出阴筊却松了口气 → 你本来就不想做）。在这个框架下随机性不只是可接受，而是**必需**——可预测的答案无法充当投射面。

## 1. 主流程

```
输入具体问题
   ↓
掷筊（动画）
   ↓
┌─ 笑筊 → 提示「问得不够具体」，可重掷（不走 LLM、不消耗额度，固定文案）
├─ 圣筊 → 落定 → 灵解（消耗 1 额度）
└─ 阴筊 → 落定 → 灵解（消耗 1 额度）

第三次仍笑筊 → 灵介入拆解问题本身（消耗 1 额度），本轮结束
   ↓
自由追问（每轮消耗 1 额度，与现状 SpiritPanel 一致）
```

### 1.1 三筊象语义

| 筊象 | 掷出形态 | 传统义 | 产品处理 |
|---|---|---|---|
| 圣筊 | 一俯一仰 | 允 | 落定，走灵解 |
| 笑筊 | 双仰 | 神明发笑：问得不清楚 | 可重掷，提示把问题问得更具体 |
| 阴筊 | 双俯 | 不允 | 落定，走灵解 |

三掷上限（防无限循环 + 控额度）。

**笑筊不走 LLM 是刻意设计**：笑筊本义就是「问题不清楚」，本来就没有可解读的内容；同时天然把额度消耗压到每轮问事最多 1 次。

## 2. 数据与存储

新表 `jiao_history`，**结构与 RLS 照抄 `dream_history`**（`supabase/migrations/0017_dream_history.sql` + `0018` 的 `full_text` 列），差异只在多一列筊象：

- `omen`：筊象（`'圣筊' | '笑筊' | '阴筊'` 之一，落定时的那次）
- `summary`：第三人称摘要（≤160 字，如「一个关于职业选择的问卦」）
- `full_text`：灵的回复全文
- **不存问题原文**——与解梦「梦原文不落库」同一条红线（owner 确认：「该不该离职/分手/做手术」这类原话敏感度不比梦低）

最近 10 条，**裁剪在应用层做**（写入后删超出的旧行），不做成 DB 触发器/RPC——沿用 `0017` 注释里写明的理由（本仓已因 security definer RPC 忘收权限出过两次生产漏洞 `0012`/`0015`）。

**续追问锚点**：点历史条目续追问时，拿 `full_text`（灵的回复全文）当锚点，不需要问题原文——EP-dream-history-2 已验证这条路可行（`continueDreamReply` 的 `dreamText: string | undefined` 重载）。

**追问轮次不落库**：`priorTurns` 随请求体即用即弃，与解梦一致。`jiao_history` 只存首次问卦。

**为什么用新表而不复用 `spirit_messages`**：后者是「逐条消息」粒度，问事的单位是「一次问卦」（含筊象），语义不同；且 `spirit_messages` 被 `merge_anon_profiles` RPC（`0012`）在事务里硬引用，不宜改动其形状。

## 3. 随机源

`crypto.getRandomValues` 在**客户端**生成两枚筊的正反（服务端往返会毁掉「掷」的即时感——掷是即时物理动作）。

**必须写死注释说明此处为何是全仓零随机原则的例外**（见 §0.1）。

## 4. 反幻觉与安全

- **筊象是既成事实，LLM 不得改写**：客户端掷出后作为事实传给 LLM。风险是模型写「你掷出了圣筊」而实际是阴筊——与四化错配同类问题，用同款后置机械校验兜：扫描输出中出现的筊象名，与实际不符即纠正。三词闭集，成本极低（同 `correctMutagens` 思路）。
- **不做宽泛关键词拦截**（假阳性会毁体验）：主要靠 prompt 硬规则——灵对任何问题都不给方向性结论，只做投射引导。
- **只机械前置拦最危险的**：自伤/医疗急症 → 不掷，直接转向求助资源。
- 复用既有 `SYNTHESIS_GUARDRAILS`（已含「不做医疗/法律/财务/生死预测」）与灵的人格 prompt 底座。

## 5. 「灵」范围收缩：周边归属变更

owner 逐项确认，四块非「问事」功能**全部保留**，但各自脱离灵的归属：

| 现状 | 变更 |
|---|---|
| 自我画像 `/spirit/portrait` + `SelfPortrait` | **挪到命盘页 `/chart`** |
| 每日问今 `AskToday`（日历页） | 留在运势页，不再算灵的一部分 |
| 风水「和 Mira 聊聊这条」（每张化解卡片内） | 改成「**就这条问一卦**」：化解动作文本预填为要问的事 → 直接进掷筊流程；**掷完之后仍可自由接着对话**（owner 明确） |
| TG bot 私聊自由对话（`lib/tg/bot.ts:87`） | 内测期保留；**记 backlog：正式上线前关闭**（owner 指示） |
| `QuickPrompts` 四条快捷提问 | 重写成问事语境示例（现为「事业方向/感情/今日运势/自我画像」，属"随便聊"语境） |

### 5.1 一条硬约束：灵的人格层删不掉

`packages/llm/src/dream.ts:103` 直接用 `buildSpiritSystemPrompt(persona, chart, language, opts) + (zh ? DREAM_RULES_ZH : DREAM_RULES_EN)` 拼出解梦的 system prompt——**解梦的人格底座就是灵的 system prompt**；`finalizeDreamOutput` 复用 `stripSpiritScaffolding`；`SpiritOptions`/`SpiritTurn` 类型也来自 `spirit.ts`。`deriveSpirit` 另被 TG 分享卡（`api/tg/card/route.ts:164`）、五行印记 `SpiritSigil` 消费。

**因此「收缩灵」能收的只是灵自己的对话 UI 与入口语义，`deriveSpirit` / `buildSpiritSystemPrompt` 这一层是共用地基，不动。**

## 6. 门控与前置

- **复用现有 `NEXT_PUBLIC_SPIRIT_ENABLED`，不新建 flag**——这是收缩现有功能而非全新功能，复用可避免两处入口（`AppShell.NAV` + `app/page.tsx` 的 `TG_ENTRIES`）flag 条件不一致的老坑（CLAUDE.md 记载的风水静默失踪教训）。
- 需登录 + 建档；未建档走 `?next=/spirit` 回跳（EP-auth-return 已建好的机制，直接复用）。

## 7. 动画

复用现有纯 CSS 模式（**本仓零动画库**，`CastingOverlay` 即是先例）：两枚筊杯抛起 → 翻转 → 落地定格。可复用 `globals.css` 已有的 `--ease-pop`（`cubic-bezier(0.34,1.56,0.64,1)`，过冲回弹曲线，适合掷落物理感）。

**`prefers-reduced-motion` 已有全局兜底**（`globals.css:141-149`，所有动画压到 0.001ms）。因此**结果不得依赖动画播完**——降级时直接出筊象。
